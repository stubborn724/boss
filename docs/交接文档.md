## 2. 当前完成情况

### 2.1 已完成模块

控制台目前包含以下模块：

1. **登录状态**
   - 查看本地登录态、浏览器/CDP 状态和平台连接状态。
   - 通过 BOSS 官方页面完成登录，不在本地页面保存或展示账号密码。
   - 支持复用已经启动的 Chrome CDP 会话，也支持由程序准备专用浏览器会话。

2. **岗位管理**
   - 同步 BOSS 职位列表。
   - 选择具体岗位，维护岗位自己的招聘标准。
   - 支持使用自然语言输入补充要求，再生成结构化规则草稿。
   - 规则需要确认后才会用于自动筛选和评分。
   - BOSS 平台硬性条件和本地岗位规则会合并使用。

3. **在线简历**
   - 刷新 BOSS 沟通列表。
   - 按全部岗位或指定岗位筛选本地列表。
   - 查看候选人的 BOSS 在线简历。
   - 可读取候选人卡片信息和沟通详情。
   - 在线简历查看和附件简历下载是两个独立动作，刷新列表不会自动索要或下载附件。

4. **BOSS 自动化**
   - 按岗位同步沟通列表。
   - 启动沟通列表自动化。
   - 启动推荐牛人自动化。
   - 暂停、继续、停止自动化。
   - 查看当前岗位处理队列、活动日志和候选人阶段。
   - 推荐牛人达到 BOSS 当日沟通上限时停止推荐牛人，并保留沟通列表处理能力。
   - 支持设置沟通列表、推荐牛人和全流程自动化的运行时间。

5. **候选人**
   - 查看已经通过岗位筛选和简历评估的候选人。
   - 查看评分、硬条件判断、语义匹配、风险信号、评分拆解和 AI 证据。
   - 查看候选人当前阶段、最近动作、下一步和待办。
   - 支持候选人池导出。
   - 候选人池按岗位隔离，同一人进入不同岗位时不会串用对话、简历或评分结果。

6. **后续跟进**
   - 管理候选人后续跟进任务和阶段记录。
   - 查看候选人的电话、微信和约面试相关结果（具体动作取决于岗位设置及自动化开关）。

7. **设置**
   - 配置每个岗位的面试邀请字段。
   - 配置换微信、换电话、约面试是否加入自动化流程。
   - 配置动作重试和退避策略。
   - 配置定时任务及其时间窗口。
   - 配置 AI 服务、模型和运行模式。

### 2.2 已完成的关键流程

当前推荐的实际流程如下：

```text
启动服务
  -> 打开 BOSS 官方页面并登录
  -> 同步 BOSS 职位
  -> 选择目标岗位
  -> 确认该岗位的硬条件、专业规则和评分规则
  -> 同步该岗位沟通列表
  -> 先处理本轮快照中的已回复/消息有变化候选人
  -> 再处理尚未首次检查的候选人
  -> 首轮非专业问题
  -> 根据候选人回复判断是否进入专业问题
  -> 判断专业问题是否已经问过，避免重复提问
  -> 读取专业问题回答并评估
  -> 达到条件后索要简历
  -> 发现附件简历后点击 BOSS 的确认/同意
  -> 下载附件简历到本地目录
  -> 使用当前岗位的已确认规则分析简历
  -> 合格候选人进入当前岗位候选人池
  -> 按设置执行换微信、换电话、约面试
  -> 在候选人页面展示结果并支持批量导出
  -> 每发送 20 位推荐牛人后回沟通列表检查
```

本轮队列固定当前沟通列表快照顺序。自动化期间新进入列表的候选人放入下一周期，避免页面变化导致当前队列跳动、重复点击或遗漏原队列中的回复。

## 3. 使用方法

### 3.1 安装依赖

项目使用 `uv` 管理 Python 环境。进入项目目录后执行：

```powershell
Set-Location D:\wqjproject\boss-agent-cli
uv sync --all-extras
```

不要直接使用系统 `pytest`，项目验证命令统一使用 `uv run`。

### 3.2 启动本地控制台

```powershell
Set-Location D:\wqjproject\boss-agent-cli
uv run boss web --port 8765
```

浏览器打开：

```text
http://127.0.0.1:8765/
```

如果 8765 端口已被占用，可改用其他端口，例如：

```powershell
uv run boss web --port 8766
```

### 3.3 登录 BOSS

1. 打开控制台的“登录状态”模块。
2. 点击打开 BOSS 登录页。
3. 使用 BOSS 官方页面完成登录。
4. 返回控制台，确认状态显示已登录。
5. 如果使用已有 Chrome，确保 Chrome 是通过 CDP 调试端口启动的；常用端口为 `9222`。

Windows 启动专用 CDP Chrome 示例：

```powershell
$chromeCandidates = @(
  "$env:ProgramFiles\Google\Chrome\Application\chrome.exe",
  "${env:ProgramFiles(x86)}\Google\Chrome\Application\chrome.exe",
  "$env:LOCALAPPDATA\Google\Chrome\Application\chrome.exe"
)
$chrome = $chromeCandidates | Where-Object { Test-Path $_ } | Select-Object -First 1
& $chrome `
  --remote-debugging-port=9222 `
  --remote-allow-origins=* `
  --user-data-dir="$env:LOCALAPPDATA\boss-agent-cdp-profile"
```

如果使用 CDP 登录：

```powershell
uv run boss --cdp-url http://localhost:9222 login --cdp
```

### 3.4 配置岗位

1. 进入“岗位管理”。
2. 点击“同步 BOSS 职位”。
3. 选择需要处理的岗位，例如 Java 或售后技术支持。
4. 在“AI 招聘标准补充”中输入自然语言要求。
5. 点击“AI 分析生成规则”。
6. 检查 BOSS 硬条件、本地补充规则、权重、阈值和专业问题。
7. 点击确认启用。

岗位配置必须逐岗位维护。Java 的技能、学历、经验、专业问题和评分阈值不会自动套用到售后技术支持岗位。

### 3.5 只刷新并查看在线简历

1. 选择“在线简历”。
2. 选择“全部岗位”或具体岗位。
3. 点击“刷新沟通列表”。
4. 等待页面提示同步成功或失败。
5. 在候选人行点击“查看在线简历”。

该操作只读取沟通列表和在线简历，不会自动发送消息、索要附件或下载附件。若用户需要附件简历，使用候选人的附件处理动作或自动化流程。

### 3.6 启动沟通列表自动化

1. 进入“BOSS 自动化”。
2. 选择目标岗位。
3. 先点击“同步沟通列表”，确认同步成功。
4. 点击“开始沟通列表自动化”。
5. 观察活动日志和当前岗位处理队列。

处理原则：

- 先固定本轮沟通列表快照。
- 优先处理已经回复、未读标记或消息版本发生变化的人。
- 已完成专业问答的人直接评估回答，不重新问专业问题。
- 已经问过非专业问题的人不重复问非专业问题。
- 已索要简历但尚未发附件的人进入等待状态，不阻塞其他候选人。
- 之前等待附件的人如果后来发来简历，会重新进入附件终审优先队列。
- 已下载、已分析、已进入候选人池的人不重复沟通。
- 当前候选人完成当前步骤后，才能切换下一个候选人。

### 3.7 启动推荐牛人自动化

推荐牛人流程按当前岗位运行：

1. 进入“BOSS 自动化”。
2. 选择目标岗位。
3. 确认岗位话术和 BOSS 推荐页面的岗位筛选一致。
4. 点击“开始推荐牛人自动化”。
5. 每发送 20 位后，系统回到沟通列表检查回复和附件状态。

推荐牛人发出的候选人后续仍会进入沟通列表，所以推荐流程不能只看推荐页。达到 BOSS 推荐牛人当日沟通上限时，系统应在页面提示原因，停止推荐牛人，继续允许沟通列表自动化处理已经产生的会话。

### 3.8 全流程自动化

全流程自动化的目标顺序是：

```text
沟通列表自动化
  -> 完成当前岗位已有会话的沟通和附件处理
  -> 每 20 位推荐牛人回沟通列表检查
  -> 推荐牛人自动化
  -> 推荐产生的新会话进入下一轮沟通列表处理
```

全流程自动化不能把推荐牛人和沟通列表当成互不相干的两条流水线。推荐牛人只负责产生新的沟通入口，后续回复、专业问答、简历和候选人池处理仍以沟通列表为准。

### 3.9 设置换电话、换微信和约面试

在“设置”中按岗位配置：

- 是否执行换微信。
- 是否执行换电话。
- 是否执行约面试。
- 三个动作的顺序。
- 失败后的退避重试。
- 约面试表单字段和邀请内容。

推荐的动作顺序是：

```text
换微信 -> 换电话 -> 约面试
```

只有简历分析达到当前岗位标准、候选人进入候选人池，并且对应自动化开关已开启，才会执行这些动作。换微信和换电话不要求都成功；只要其中一个成功，在约面试自动化开启的前提下即可进入约面试。两个动作失败时按设置重试，不能因为一个动作失败就误判整个候选人流程。

### 3.10 简历和联系方式导出

当前支持两类简历：

1. **在线简历**：在 BOSS 平台中查看，主要用于快速确认候选人信息；本地控制台可以触发打开预览。
2. **附件简历**：候选人发送附件后，在 BOSS 中点击确认/同意，下载到本地后再进行正式解析和评分。

默认本地输出目录按运行上下文计算。Windows 桌面目录通常为：

```text
C:\Users\<用户名>\Desktop
```

项目内部的招聘者导出默认目录为数据目录下的 `recruiter/resumes`；Web 控制台会根据上下文使用桌面或上下文专属目录。实际以页面成功结果中的“路径”为准，不要只凭文件名判断是否已经保存。

联系方式目前只在候选人页面显示，并提供 CSV/Excel 批量导出能力。导出对象限定为当前岗位下已经达到标准的候选人，不导出未通过硬筛、未完成分析或其他岗位的联系方式。

## 4. 规则、状态和评分说明

### 4.1 岗位上下文

自动化每个步骤都使用一个明确的岗位上下文，包含：

- 本地 `job_id`。
- BOSS 的岗位 ID。
- 岗位名称。
- BOSS 平台硬条件快照。
- 本地已确认规则。
- 配置版本。
- 评分权重和阈值。
- 专业问题及对话配置。

任何自动化模块都不应读取全局“当前岗位”来拼接规则。缺少岗位、规则未确认或 BOSS 条件与本地规则冲突时，应阻止自动判断并在页面显示具体原因。

### 4.2 对话阶段

候选人对话应按以下状态判断，而不是简单根据候选人是否出现在当前页面判断：

1. 首次检查：没有历史阶段和有效消息游标。
2. 已发非专业问题：等待候选人回复。
3. 非专业问题已回复：根据回答决定是否进入专业问题。
4. 已发专业问题：等待候选人回复。
5. 专业问题已回复：立即评估回答，不能再次发送专业问题。
6. 已索要简历：等待附件或在线简历状态变化。
7. 已收到附件：优先执行 BOSS 附件确认、下载和分析。
8. 已分析：根据岗位标准进入候选人池或记录不通过原因。
9. 已完成：不再重复沟通。

消息判断需要同时参考未读标记、最后一条候选人消息、消息版本或时间游标、我方最后一条消息和本地持久化阶段。单独依赖“未读”容易漏掉已经点开聊天框后才到达的新消息。

### 4.3 简历评分

评分分为三层：

1. **BOSS 平台硬条件**：学历、经验、城市、薪资、职位等平台条件。
2. **本地确定性规则**：岗位技能、年限、行业经历、稳定性、业务要求等。
3. **AI 语义辅助**：只提取可在简历正文中核对的语义证据，不直接替代硬筛，也不在规则不明确时编造结论。

Java 与售后技术支持等不同岗位使用各自的标准、权重和专业问题。同一份简历在不同岗位下得到不同评分是正常行为；历史结果保留，不会因为新岗位规则上线而自动重算历史评分，新收到的简历使用对应岗位的新版本规则。

### 4.4 候选人池准入

进入候选人池的前提是：

- 当前岗位上下文有效。
- BOSS 硬条件没有明确不匹配。
- 专业问题已完成并且回答已评估。
- 附件简历已成功确认、下载和解析，或当前流程明确允许在线简历评分。
- 最终评分达到当前岗位阈值。
- 必要时通过已有人工复核门禁。

已经进入候选人池的候选人不应再次进入普通打招呼或重复问答流程。

## 5. 数据、接口和代码结构

### 5.1 主要入口

本地 Web API 位于 `src/boss_agent_cli/web/app.py`，运行时状态和后台任务位于 `src/boss_agent_cli/web/runtime.py`。

常用接口：

| 接口 | 用途 |
|---|---|
| `GET /api/state` | 查看登录态、自动化、同步、导出和岗位状态 |
| `GET /api/recruiting/workspace` | 读取当前岗位工作台 |
| `GET /api/recruiting/automation/settings` | 读取岗位自动化设置 |
| `POST /api/recruiting/automation/settings` | 保存岗位自动化设置 |
| `GET /api/recruiting/automation/schedules` | 读取定时任务 |
| `POST /api/recruiting/automation/schedules` | 保存定时任务 |
| `POST /api/recruiting/automation/sync` | 同步岗位沟通列表 |
| `POST /api/recruiting/automation/start` | 启动沟通列表或推荐牛人自动化 |
| `POST /api/recruiting/automation/pause` | 暂停自动化 |
| `POST /api/recruiting/automation/resume` | 继续自动化 |
| `POST /api/recruiting/automation/stop` | 停止自动化 |
| `POST /api/conversations/{selection_id}/online-resume/open` | 打开在线简历预览 |
| `POST /api/recruiting/automation/candidates/{candidate_key}/actions` | 执行候选人后续动作 |
| `GET /api/recruiting/automation/candidate-pool/export` | 导出当前岗位候选人池 |

### 5.2 主要模块职责

- `web/app.py`：HTTP 路由、请求校验、统一 JSON 错误响应。
- `web/runtime.py`：控制台运行时、后台线程、任务状态、BOSS 平台串行访问和超时守卫。
- `web/assets.py`：本地控制台 HTML、CSS 和浏览器端交互逻辑。
- `recruiting/job_context.py`：解析岗位有效上下文，阻止跨岗位规则串用。
- `recruiting/automation_coordinator.py`：候选人队列、阶段推进、回复优先和周期调度。
- `recruiting/automation_queue.py`：岗位候选人队列持久化。
- `recruiting/dialogue_state.py`：对话阶段、问题去重和消息游标。
- `recruiting/automation_state_projection.py`：从历史状态恢复候选人展示状态。
- `recruiting/interview_settings.py`：岗位级约面试和后续动作设置。
- `recruiting/automation_schedule_settings.py`：岗位级定时任务设置。
- `commands/recruiter/communication_pipeline.py`：沟通、附件确认、下载和分析流水线。
- `commands/recruiter/attachment_index.py`：附件状态和已下载简历索引。
- `commands/recruiter/resume_parser.py`：简历正文解析。
- `recruiting/ai_review.py`：AI 语义评估和可验证证据提取。
- `platforms/zhipin_recruiter.py`：招聘者平台能力适配。
- `rpa/boss_client.py`：BOSS 页面选择、点击、确认、下载和回执读取。

### 5.3 持久化边界

数据目录由 `--data-dir` 决定，默认通常为用户目录下的 `.boss-agent`。候选人状态、岗位配置、沟通游标、任务计划、附件索引和日志都应放在本地数据目录或明确的输出目录中。

以下内容不得提交到 Git 或上传远程仓库：

- 本地简历正文和 PDF。
- BOSS Cookie、Token、登录态和浏览器用户目录。
- 运行日志和调试转储。
- 临时目录、IDE 配置和本机数据库。

仓库已经通过 `.gitignore` 忽略常见的 `data/`、`recruiter/`、`*.log`、`.tmp/` 和 `.idea/` 等本地内容，但新增输出目录时仍需人工复查。

## 7. 历史问题与排查方法

### 7.1 “显示未登录”但 BOSS 页面实际已登录

可能原因：

- 控制台连接的不是实际登录的 Chrome 会话。
- CDP 端口变化或 Chrome 被重新启动。
- 使用了不同的数据目录。
- BOSS Cookie 过期或浏览器上下文正在切换。

排查顺序：

1. 确认 BOSS 官方页面能正常打开且已登录。
2. 确认 Chrome 使用 `--remote-debugging-port=9222` 启动。
3. 确认控制台启动时使用了正确的 `--cdp-url`。
4. 在“登录状态”页重新探测。
5. 仍失败时执行 `uv run boss doctor` 和 `uv run boss status --live`。
6. 最后再重新登录，不要在未确认连接对象时反复点击同步。

### 7.2 “同步沟通列表超时”

可能原因：

- BOSS 页面不在沟通列表。
- 页面仍在刷新或岗位筛选切换中。
- CDP/RPA 会话断开或被另一个任务占用。
- BOSS 列表数量大，超过单次读取预算。
- 后台任务已经超时，但浏览器端仍残留旧操作。

当前设计会先校验登录和岗位筛选，再读取沟通列表；失败时保留最后一次成功快照，不应把旧数据伪装成新同步结果。

处理方式：

1. 暂停或停止正在运行的自动化。
2. 手动回到 BOSS 沟通列表页面。
3. 确认岗位筛选正确，选择“全部岗位”时确认 BOSS 页面确实回显全部岗位。
4. 等待页面稳定后重新点击同步。
5. 查看页面提示和 `/api/state`，确认任务从 `running` 变为 `succeeded` 或 `failed`。
6. 连续失败时运行 `uv run boss doctor --live-probe`，不要无限重试。

### 7.3 一直轮询、没有进入下一步骤

重点检查候选人阶段：

- 是否已经发过非专业问题但没有回复。
- 是否已经发过专业问题但没有回复。
- 是否已经索要附件但附件尚未发送。
- 是否已经收到附件但附件确认或下载任务失败。
- 是否消息游标没有更新，导致系统无法判断新回复。
- 是否旧状态与当前岗位不一致，导致状态被安全地视为未知。

正确行为是：等待中的候选人不能阻塞整个队列；系统应跳过当前等待状态，继续处理其他候选人，并在下一轮优先检查消息或附件发生变化的人。

### 7.4 专业问题或非专业问题重复发送

判断重复问题不能只看当前页面文本。应检查：

- 当前岗位和候选人联合状态键。
- 我方最近已发送的问题。
- 对方回答是否已经落在该问题之后。
- 问题指纹或语义去重结果。
- 配置版本是否发生变化。

如果候选人已经回答专业问题，下一步应是评估回答和决定是否索要简历，而不是再次提问。配置升级后，当前候选人的当前步骤原则上完成后再切换新版本，避免中途改变问题。

### 7.5 已收到简历但没有处理

常见原因是流程只按顺序向下扫描，没有单独维护“待附件终审”队列。正确处理方式：

1. 每轮先扫描已有候选人的消息和附件状态变化。
2. 已收到附件的人进入最高优先级。
3. 打开对应聊天框时校验 `friend_id`，避免误点其他候选人。
4. 点击 BOSS 的附件确认/同意按钮。
5. 读取下载回执和文件大小。
6. 将附件导入当前岗位的分析流程。
7. 分析完成后再决定是否进入候选人池和执行后续动作。

### 7.6 点击暂停后仍在运行

暂停是协作式停止：当前正在执行的平台原子动作可能会完成，随后不再开始下一位候选人。检查页面状态是否显示“已请求暂停”以及活动日志是否还有最后一条收尾记录。

如果持续产生新动作：

1. 点击“停止”而不是“暂停”。
2. 刷新 `/api/state`。
3. 检查是否存在旧服务进程或重复启动的本地控制台。
4. 关闭重复进程后重新启动单个服务。

### 7.7 点击按钮没有反应或保存显示失败

先看按钮旁边的提示，不要只看页面是否跳转。前端请求是异步的，保存成功或失败会写入 `aria-live` 提示。

排查：

- 浏览器开发者工具 Network 中检查接口返回状态。
- 检查请求是否包含同源 `Origin`。
- 检查是否把业务数据误当成完整 HTTP Response。
- 检查当前岗位 ID 是否为空。
- 检查设置字段是否通过后端校验。
- 查看 `/api/state` 是否有后台任务失败。

### 7.8 在线简历按钮没有反应

在线简历预览依赖候选人的已校验 `friend_id`，姓名不是身份标识。确认：

- 当前列表来自最近一次成功同步。
- 候选人没有被切换到其他岗位列表。
- BOSS 页面仍然登录并可访问该候选人。
- 当前 RPA 会话没有被其他后台任务占用。

如果 BOSS 页面可以打开但本平台没有内容，查看接口返回的 `state`、`error.code` 和 `recovery_action`，不要直接重复点击造成多个后台任务竞争。

### 7.9 岗位筛选显示旧岗位或“未标注岗位”

BOSS 页面是有状态页面，切换岗位后不能只修改本地下拉框。必须：

1. 在 BOSS 页面实际切换岗位。
2. 读取并校验页面回显。
3. 再读取沟通列表。
4. 本地结果写入当前岗位上下文。

“未标注岗位”代表平台数据没有可靠岗位标识，不能擅自归入 Java 或其他岗位；应保留为未知并提示用户处理。

## 8. 安全、合规和运行边界

项目默认是低风险、用户主动触发模式。招聘者候选人简历、聊天、联系方式、消息发送和批量平台写操作涉及个人信息和平台风控，必须在明确授权、明确运行模式和可审计条件下使用。

运行时应遵守：

- 不绕过 BOSS 登录、验证码、风控或安全页。
- 遇到账号风险、验证码或安全拦截立即停止访问。
- 不把 Cookie、Token、简历正文和联系方式写入日志或提交 Git。
- 不把候选人姓名当作平台身份键，平台动作使用经过校验的 ID。
- 所有后台任务都必须有停止开关、超时、失败回执和状态展示。
- 不因为 AI 失败而编造评分或淘汰结论。
- 条件未知时记录未知，不把未知当作不合格。
- 执行敏感操作前确认当前岗位和当前候选人没有串线。

## 9. 未来建议优化项

### 9.1 自动化可靠性

1. 将“消息变化扫描”“附件变化扫描”“普通候选人推进”拆成三个明确队列，并为每个队列提供可见计数。
2. 为每个候选人增加最后扫描时间、最后推进时间、阻塞原因和下一次重试时间。
3. 对单个候选人的等待状态设置最大等待周期，超过后记录为“长期未回复”，避免看起来像卡死。
4. 增加任务心跳和 watchdog 页面，明确区分“正在等待候选人回复”和“后台线程卡住”。
5. 将 BOSS 页面切换、列表读取、聊天框打开和附件下载的超时分别统计，不再只显示一个总超时。
6. 支持任务恢复时从持久化 checkpoint 继续，而不是重新扫描后依赖模糊状态推断。

### 9.2 简历处理

1. 为附件确认、下载、解析和评分增加独立状态机及失败重试次数。
2. 增加文件哈希，避免同一附件重复分析。
3. 支持保留历史简历快照，而不是只覆盖同名文件。
4. 在候选人页面显示“附件发现时间、确认时间、下载时间、分析时间和分析版本”。
5. 在线简历和附件简历都提供清晰的来源标签，避免用户误以为“查看在线简历”已经完成附件下载。

### 9.3 岗位配置和评分

1. 增加岗位配置版本对比和回滚。
2. 展示 BOSS 条件与本地条件冲突的逐字段差异。
3. 增加评分解释的固定示例和人工复核入口。
4. 对“硬条件未知”“AI 无法核验”“证据不足”分别展示，不合并成笼统低分。
5. 对每个评分结果保存规则版本、岗位 ID、证据引用和运行时间。

### 9.4 UI 和可观测性

1. 所有按钮统一显示“已接收、执行中、成功、失败、已跳过”状态。
2. 将轮询日志转换为候选人级别的可读事件时间线。
3. 在自动化顶部显示：当前岗位、当前阶段、当前候选人、队列数量、等待数量、附件待处理数量和最近进度时间。
4. 增加任务运行报告导出，方便交接和审计。
5. 对定时任务显示下次执行时间、上次结果、停止原因和当前是否在工作时间窗口内。

### 9.5 测试与发布

1. 增加真实 Chrome/CDP 的受控冒烟测试，但测试账号必须与生产账号隔离。
2. 增加列表 793 人、消息变化、附件延迟到达、岗位切换和重复启动等压力场景。
3. 增加服务重启、浏览器崩溃、网络断开和登录过期后的恢复测试。
4. 每次发布前固定执行全量测试、Ruff、MyPy 和 `git diff --check`。
5. 发布前自动检查仓库是否包含 PDF、Cookie、Token、日志和本地数据库。
