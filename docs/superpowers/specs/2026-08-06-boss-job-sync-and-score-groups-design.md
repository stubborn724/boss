# BOSS 职位同步与候选人分组设计

## 目标

将当前招聘账号在 BOSS 上的已发布职位以只读方式同步到本地招聘工作台。每个
本地岗位必须与唯一的平台职位标识绑定，并独立拥有岗位标准、知识库、候选人
关联、评估报告和分数分组。用户同时招聘两个岗位时，同一候选人在不同岗位下
可以有不同的评估结果，系统不得把一个岗位的标准或流程状态带入另一个岗位。

本设计以《智能人事 AI》需求文档为评分与流程依据：硬条件、岗位经验、专业
问答、沟通表达、稳定性、薪资/时间/地点六个维度分别占 25%、20%、25%、15%、
10%、5%；结论必须保留证据、风险与人工复核边界。

## 范围与边界

本轮覆盖：

- 只读同步 BOSS 已发布职位到当前企业/账号上下文的本地工作台；
- 每个 BOSS 职位创建或更新一个本地岗位镜像；
- 读取桌面目录中的 Markdown、TXT 和文字型 PDF 简历，导入后按所选岗位评估；
- 在招聘工作台中按“岗位 -> 分数段”组织候选人，并显示证据、风险和下一步；
- 对现有 CLI `hr screen` 和 Web 工作台共用同一套本地文本读取、评分和分组投影。

明确不做：

- 不自动发送 BOSS 消息、索要简历、交换联系方式、添加私域或安排面试；
- 不以性别、婚育、民族、户籍等敏感信息参与解析或评分；
- 不把简历正文、联系方式或平台原始响应复制到 Web 快照、日志或列表接口；
- 不因同步操作自动发布本地岗位或覆盖 HR 已确认的岗位标准。

## 方案

### 1. 职位镜像

新增一个受限的职位镜像领域能力，而不是把平台职位名称临时塞进现有岗位表单。
本地 `JobProfile` 增加可选的来源元数据：

- `source`：`manual` 或 `boss`；
- `platform_job_id`：BOSS 返回的加密职位标识，作为当前账号上下文内的唯一键；
- `platform_snapshot`：仅保留职位名称、城市、薪资、描述摘要和平台状态等业务字段；
- `last_synced_at` 与 `platform_sync_status`：记录最近一次同步结果和时间。

同步使用已存在的 BOSS 职位读取通道，并保持 Research Mode、已登录和错误码边界。
适配层从不同平台返回形状中安全提取可用字段；字段不存在时保留为空，不用推测值。

同步规则：

1. 同一上下文内按 `platform_job_id` 查找镜像；找到则更新平台快照。
2. 找不到时新建本地草稿岗位，名称、城市和薪资来自可用的平台字段。
3. 同步只更新平台快照，不覆盖 HR 填写的 `criteria`、评分权重、知识库、FAQ、问答
   开关、人工备注和发布状态。
4. 新镜像默认是草稿；HR 补齐或确认文档要求的岗位标准后才可发布并用于评分。
5. 平台职位不再出现在本次同步结果时只标记镜像“平台侧未发现”，不删除本地历史。

这条规则把“平台事实”和“HR 招聘决策”分开，避免一次刷新清空已审核的配置。

### 2. 简历读取与岗位评估

新增本地简历文本读取器，职责仅是按文件类型返回文本和最小元数据：

- Markdown/TXT 以 UTF-8 读取；
- PDF 用受维护的 PDF 文本提取库读取文字层；
- 文件不存在、超限、加密、损坏或没有文字层时返回稳定错误码与恢复建议；
- 解析出的文本仅在导入和评估调用期间存在，不写入工作区 JSON、Web 响应或日志。

现有候选人与岗位多对多关联继续作为事实来源。评估始终以 `(本地岗位 ID, 候选人
ID)` 为键保存，分数不能覆盖其他岗位下的报告。评分器继续使用需求文档已经定义的
六项权重和三层筛选（硬条件、语义匹配、风险识别），并保留专业问答、风险、证据和
人工门禁。

### 3. 候选人列表分组

新增纯投影函数，输入当前岗位的候选人关联和评估报告，输出固定顺序的分组：

- `strongly_recommended`：90-100，强烈推荐；
- `recommended`：80-89，推荐；
- `pending_confirmation`：70-79，待确认；
- `manual_review`：60-69，人工复核；
- `not_recommended`：0-59，不推荐；
- `unassessed`：没有该岗位评估报告。

每个候选人只在当前岗位的一个分组中出现。卡片只显示姓名、来源、阶段、分数、风险
等级、命中证据摘要和下一步；点击后复用现有评估/待办入口。候选人可同时出现在两个
岗位的不同分组内，这表示两份独立评估，而不是重复数据。

工作台在“处理队列”顶部增加“同步 BOSS 职位”操作及最后同步状态，在“评估与复盘”
中提供按岗位切换的分组列表。同步和刷新都只读取平台，不触发候选人外部动作。

## 数据流

```text
BOSS 职位列表（只读、Research Mode）
  -> 职位归一化与字段白名单
  -> 本地岗位镜像（按 platform_job_id 幂等 upsert）
  -> HR 确认岗位标准并发布

本地简历 MD/TXT/PDF
  -> 文本读取器（正文不持久化到状态）
  -> 候选人与岗位关联
  -> 按岗位标准评分并保存报告
  -> 岗位内分数段投影
  -> 候选人列表 / 处理队列
```

## 错误处理与兼容性

- 未开启 Research Mode、登录失效、网络失败和平台字段缺失均返回现有受控错误码；
- 同步失败不删除旧镜像和既有评估；
- 无法提取 PDF 文字时，该文件单独标记失败，批量中的其他简历继续处理；
- 旧版手工创建的岗位默认 `source=manual`，不需要迁移即可继续工作；
- 现有多企业/多账号 `RecruitingContext` 是镜像唯一性的第一层边界，任何同步数据
  不能跨上下文读取或写入。

## 测试与验收

- 职位归一化：不同平台响应形状、状态过滤和字段缺失；
- 同步服务：首次创建、重复幂等、更新平台快照、保留 HR 标准、平台职位消失；
- PDF 读取：正常文本、空文字层、损坏/加密/超限和 Markdown/TXT 回归；
- 评估：同一候选人绑定两个岗位，分别得到独立报告；
- 分组：六个分组边界、固定排序、未评估候选人和跨岗位隔离；
- Web API 与页面：同步按钮、岗位选择、分组展示和异常提示；
- 全量现有测试、Ruff 与 MyPy 回归。

## 验收结果

1. BOSS 上的两个职位可在当前平台中分别看到，且再次同步不会重复创建。
2. 两个职位各自拥有独立岗位标准和评分结果。
3. 桌面 `C:\\Users\\25479\\Desktop\\简历` 中的两份 PDF 能进入对应岗位候选人列表。
4. 每份简历在对应岗位中显示在文档定义的分数段，且有证据、风险和人工下一步。
5. 所有平台沟通、私域和面试动作仍保持人工触发与人工回填。
