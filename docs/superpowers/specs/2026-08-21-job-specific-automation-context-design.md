# 岗位专属自动化上下文设计

## 目标

让每个岗位的 BOSS 基础条件、本平台自然语言补充规则、评分权重和专业问答配置，
完整影响该岗位后续的自动沟通、附件简历分析、候选人评分和候选人池准入。不同
岗位之间不得复用通用标准、串用对话状态或覆盖分析结果。

本设计是在现有模块上做强边界改造：保留已经运行的沟通状态机、专业问题生成、
候选人池、附件下载和自然语言规则生成能力，只统一岗位配置的来源、版本和传递
方式，不重写现有招聘流程。

## 已确认的业务规则

1. BOSS 同步岗位名称、城市、薪资、学历、描述和平台状态等基础事实。
2. 本平台按岗位保存技能、必须条件、优先条件、淘汰条件、评分权重和阈值。
3. 岗位管理继续支持自然语言输入，由 AI 将补充要求转换为结构化建议规则。
4. 规则不完整时可以由 AI 生成建议，但必须在岗位编辑页逐项确认后才能启用。
5. BOSS 条件与本地规则合并使用；同步不得静默覆盖已确认的本地规则。
6. 两类条件冲突时标记冲突并阻止启用，用户确认最终值后生成新的配置版本。
7. 每个岗位独立配置评分权重和通过阈值。
8. 已确认的新版本立即生效；当前候选人的当前步骤使用原版本完成，下一步骤读取
   最新版本。
9. 明确不符合硬性条件时立即停止该候选人在当前岗位的流程并记录原因；信息不明确
   时忽略该项并继续沟通。
10. 专业问题生成、已问问题去重和合格候选人进入候选人池的行为沿用现有实现。
11. 候选人进入候选人池后结束该岗位的 BOSS 自动沟通，不再重复提问。
12. 历史对话和历史分析结果不迁移、不重算；新版本只影响其确认后的新步骤和新简历。

## 配置模型

### BOSS 基础条件

BOSS 同步结果作为只读平台快照保存，字段包括岗位名称、城市、薪资、学历、岗位
描述和平台状态。再次同步只更新平台快照，不能删除或覆盖人工确认的补充规则。

### 本平台补充规则

每个岗位独立保存：

- 技能列表；
- 必须条件、优先条件和淘汰条件；
- 六项评分权重；
- 初筛、推荐和专业问答阈值；
- 专业问答开关及现有专业问题生成所需配置；
- 规则状态、配置版本、确认时间和确认来源。

AI 生成结果先进入草稿。草稿可以编辑，但不能供自动化筛选、淘汰、评分或推进。
用户点击“确认启用”后，系统校验字段、权重总和、阈值和平台条件冲突，然后生成
不可变的已确认版本。

### 有效岗位上下文

新增专门的岗位上下文解析服务。调用方只传 `job_id`，解析服务返回当前已确认的
有效配置，内容由 BOSS 平台快照和本地补充规则合并而成。上下文必须携带：

- 本地 `job_id` 和 BOSS `platform_job_id`；
- 岗位名称和配置版本；
- 合并后的硬性条件、技能和评分参数；
- 配置状态及冲突诊断。

任何自动化模块不得自行拼接规则、读取“当前岗位”全局变量或回退到“通用岗位”。
岗位不存在、规则未确认或存在冲突时，阻止对应自动判断并返回明确提示。

## 自动化数据流

```text
启动岗位自动化(job_id)
  -> 解析该岗位最新已确认上下文
  -> 同步该 BOSS 岗位的沟通列表
  -> 按岗位硬性条件处理基础阶段
  -> 沿用现有逻辑生成并去重专业问题
  -> 按岗位标准评估专业回答
  -> 下载候选人附件简历
  -> 按同一岗位上下文执行正式评分
  -> 通过现有人工复核门禁
  -> 合格者进入该岗位候选人池并结束自动沟通
```

每个候选人的每个步骤开始时读取一次最新已确认版本，并把该版本固定到步骤结束。
步骤执行期间确认了新版本时，不中断当前平台动作；下一个步骤自动切换并记录新版本。

## 状态隔离与兼容

自动化队列已经使用 `job:{job_id}:friend:{friend_id}` 作为联合键。对话状态、消息
游标、附件状态和分析结果也必须按岗位与候选人联合隔离，避免同一候选人在 Java
和售后技术支持岗位之间串题、串附件或串评分。

现有历史状态继续按原规则读取，不批量迁移或重新分析。新建状态使用联合键；读取
旧状态时只有其 `job_id` 与当前岗位一致才允许兼容使用，否则视为当前岗位无状态。

## 附件简历分析

当前共享 `CommunicationPipeline` 未在附件终审调用中获得具体岗位，是本次需要修复
的核心边界。附件终审必须显式接收有效岗位上下文，禁止使用空标准。

附件分析复用招聘工作台的正式评分模型：程序根据岗位配置计算六项分数，AI 只做
语义匹配和可验证证据提取。删除附件终审中针对销售、客服等通用关键词的岗位无关
兜底；AI 不可用或证据不足时转入现有人工复核门禁，不生成误导性岗位分数。

新分析结果保存岗位 ID、岗位名称、配置版本、各维度分数、证据和结论。历史分析
结果保持原样，不因本次上线自动覆盖。

## 错误与冲突处理

- BOSS 同步失败：保留最后一次平台快照，不清空岗位规则，提示同步失败原因。
- 本地规则未确认：禁止启动该岗位的自动筛选并引导到岗位编辑页确认。
- BOSS 条件与本地规则冲突：展示具体字段和值，确认前禁止启用新版本。
- 岗位在运行中被删除或失效：完成已开始的平台原子动作后停止下一步骤。
- 候选人信息不明确：记录未知，不据此淘汰，继续现有沟通流程。
- 候选人明确违反硬性条件：记录条件、候选人证据和配置版本，结束当前岗位流程。
- AI 不可用：不使用通用关键词伪造岗位评分，进入人工复核。

## 页面行为

岗位编辑页保留自然语言输入和“AI 分析生成规则”。生成后展示 BOSS 基础条件、AI
建议和人工编辑结果，用户可以逐项修改并点击“确认启用”。页面同时显示当前版本、
确认状态、冲突项和评分权重总和。

候选人分析结果显示实际使用的岗位、配置版本、硬性条件判断、六项得分、证据和未
推进原因，便于解释同一份简历在不同岗位下为什么得到不同结论。

## 测试与验收

1. BOSS 再次同步只更新平台快照，并保留自然语言生成后已确认的本地规则。
2. AI 建议未确认时不能启动自动筛选；确认后生成独立岗位版本。
3. Java 和售后技术支持使用不同技能、权重、阈值和专业判断。
4. 同一份新简历按两个岗位分析时，证据和各维度结果按岗位独立生成。
5. 附件终审必须收到对应 `job_id` 的有效上下文，缺失时不得回退通用岗位。
6. 同一候选人在两个岗位中的对话和附件状态互不覆盖。
7. 配置在当前步骤执行期间更新时，当前步骤保留旧版本，下一步骤使用新版本。
8. 明确违反硬性条件时停止当前岗位流程；条件未知时继续沟通。
9. 合格候选人进入候选人池后不再被 BOSS 自动化重复沟通。
10. 历史评分不重算，附件下载、暂停、定时任务和推荐牛人现有行为不回归。
11. 相关单元测试、Web API 测试、自动化流程测试、Ruff 和全量测试通过。
